## **3. Global discrepancies across character creation**

**Screen proportions**

High priority

The actual controls are compressed vertically, leaving large unused areas on pages 1 and 2, while pages 3 and 4 overflow the available space.

**Typography**

High priority

Almost everything uses the same italic treatment. The approved designs have distinct title, heading, label, value and descriptive-text hierarchies.

**Borders and framing**

High priority

Current borders have thin, interrupted edges and several appear open at the bottom. Approved borders are complete, illuminated and ornamental, with consistent corners.

**Navigation tabs**

Medium priority

Actual tabs are four equal-width bars spanning almost the entire screen. Approved tabs are compact, icon-led, connected by decorative diamonds and highlight the active stage.

**Portrait frame**

High priority

Actual portrait frames are narrow capsules with sparse ornamentation. Approved frames are wider, taller and considerably more elaborate.

**Reference panel**

High priority

The approved panel has its own heading, subject heading, icon, divider, readable description and scenic artwork. The actual panel is largely empty or displays unformatted database content.

**Navigation buttons**

High priority

Exit, Back, Save Draft and Next appear small and shallow. Approved buttons have stronger padding, closed borders and a prominent illuminated primary action.

**Spacing and padding**

High priority

Text frequently touches panel edges. Approved designs use deliberate inner margins, consistent gutters and separation between headings and content.

**Artwork integration**

Medium priority

The hall background is recognisable, but the foreground panels, portrait ornamentation, lighting effects and reference illustrations do not yet reproduce the approved composition.

## **5. Confirmed source-code causes**

I have also inspected the relevant live GDScript files. Several of the visual problems can now be traced directly to the implementation rather than inferred from screenshots.

| Source finding                              | Consequence                                                                                     |
| ------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| Font sizes multiplied by `0.64`             | Undersized typography throughout                                                                |
| Icon sizes multiplied by `0.65`             | Reduced visual prominence                                                                       |
| Control heights multiplied by `0.58`        | Shallow fields and buttons                                                                      |
| Panel content margins multiplied by `0.5`   | Insufficient internal padding                                                                   |
| Creator buttons have a minimum height of 23 | Compressed navigation and selection controls                                                    |
| Shared creator central `ScrollContainer`    | Whole-page central scrolling instead of fitted page layouts                                     |
| Portrait column minimum width of 174        | Narrow portrait presentation                                                                    |
| Reference column minimum width of 245       | Inflexible allocation across different pages                                                    |
| Sheet manager minimum body width of 780     | Sheet sizing is not properly tied to the available viewport                                     |
| Sheet horizontal scrolling disabled         | Prevents navigation of a sheet enlarged beyond viewport width unless another mechanism is added |

The recurring reduction factors affect `character_creator.gd`, `full_character_sheet.gd` and `character_manager.gd`.

**The implementation plan is to replace these blanket reductions with design-specific dimensions and responsive layout rules.** Simply removing all reduction factors without restructuring the layouts would create further overflow.

## **10. Testing strategy**

The existing layout smoke test is insufficient to establish visual fidelity. It needs to check actual control boundaries, visibility, available dimensions and overflow rather than merely minimum sizes.

| Test                         | Required validation                                                 |
| ---------------------------- | ------------------------------------------------------------------- |
| `layout_smoke.gd`            | All creator stages fit; sheet viewport and zoom behave correctly    |
| `character_smoke.gd`         | Character mechanics and selections remain correct                   |
| `sqlite_smoke.gd`            | Database integration and persistence remain functional              |
| `assets_smoke.gd`            | Artwork and optional asset handling                                 |
| Manual screenshot comparison | Five-screen comparison against approved designs                     |
| Save/reload regression       | Existing and newly created characters remain intact                 |
| Windows runtime              | Actual visual rendering, mouse interaction and fullscreen behaviour |

Testing must include spellcasting and non-spellcasting classes, different racial choices, extensive inventory, lengthy feature descriptions and characters with and without portraits.

The approved example artwork contains illustrative character statistics and spell selections. These are visual references, not authoritative mechanical test fixtures. Actual values must always come from the character rules engine.

## **11. Outstanding issues requiring acknowledgement**

Three aspects of the implementation require particular care:

**Existing controls not shown in the approved designs.** Backstory, portrait selection, AI generation, ability swapping, additional language selections and equipment choices must remain functional. Their precise placement requires integration into the approved layout.

**Artwork fidelity.** The approved frames and decorative effects are more elaborate than the current runtime assets. Exact reproduction may require creating additional matching transparent graphical components. The approved designs themselves will not be replaced.

**Begin Adventure.** The approved final page includes this button, but the campaign runtime does not yet exist. It cannot be fully functional within this development scope.

Additionally, the current environment has not independently executed the Windows build. Your screenshots are valuable runtime evidence, but they do not establish that every character operation or scrolling interaction works.
